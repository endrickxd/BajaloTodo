## 2024-10-11 - Mitigating Server-Side Request Forgery (SSRF) and understanding DNS Rebinding TOCTOU
**Vulnerability:** The application was fetching media content from URLs returned by an external Cobalt API directly using `requests.get()` without validating the underlying IP addresses. This could lead to a Server-Side Request Forgery (SSRF) vulnerability if the API or an attacker-controlled endpoint returned a URL pointing to internal infrastructure (e.g., `127.0.0.1`, `169.254.169.254`, or internal subnet IPs).
**Learning:** Preventing SSRF requires deep validation of the resolved IP addresses before the request is made. Disabling automatic redirect tracking in the HTTP client (e.g., `allow_redirects=False`) is crucial so each hop can be explicitly validated. Furthermore, application-layer DNS resolution (`socket.getaddrinfo`) and subsequent validation introduces an inherent Time-of-Check to Time-of-Use (TOCTOU) DNS rebinding limitation, as the underlying IP may change between the validation check and the actual data retrieval request made by the HTTP library.
**Prevention:** Always validate all resolved IP addresses against restricted ranges (private, loopback, link-local, multicast, unspecified) before making outbound requests using user-supplied or untrusted URLs. Implement manual redirect handling loops that apply this validation at every hop, and be mindful of the TOCTOU constraints associated with application-level DNS resolution.
