## 2024-10-12 - [Critical] Server-Side Request Forgery (SSRF) via External API Redirects
**Vulnerability:** The application fetches external URLs returned by the Cobalt API directly using `requests.get()` without validation. This creates a critical Server-Side Request Forgery (SSRF) vulnerability. An attacker or a compromised Cobalt instance could provide a redirect or a direct URL pointing to internal infrastructure (e.g., `http://169.254.169.254`, `http://127.0.0.1`, or `http://localhost:8000`), forcing the server to make requests to private IP addresses and potentially expose sensitive data or perform unauthorized actions. By default, `requests.get()` follows redirects, meaning even if the initial Cobalt API response seems safe, it could redirect to a malicious internal IP.
**Learning:** When interacting with external APIs that provide URLs for the application to fetch, the returned URLs must be rigorously validated before the request is made. Furthermore, if the request client (like `requests`) automatically follows redirects, the validation is bypassed on subsequent requests. Resolving the hostname to an IP address using `socket.getaddrinfo` is essential to check against restricted IP ranges. However, this introduces a Time-of-Check to Time-of-Use (TOCTOU) limitation: an attacker could employ DNS rebinding, where the DNS record returns a safe IP during validation but changes to an internal IP during the actual request.
**Prevention:**
1.  **Validate IPs, not just hostnames:** Use robust methods like `socket.getaddrinfo` to resolve the hostname and check if *any* of the returned IP addresses fall into restricted ranges (private, loopback, link-local, multicast, or unspecified like 0.0.0.0).
2.  **Disable automatic redirects:** Configure the HTTP client (e.g., `requests.get(..., allow_redirects=False)`) to prevent automatic following of redirects.
3.  **Implement manual redirect handling:** If redirects are expected, manually handle them in a loop. For each redirect (HTTP 3xx status), validate the new `Location` header URL before making the subsequent request. Ensure intermediate responses are explicitly closed to avoid resource leaks.
4.  **Acknowledge TOCTOU:** Document the inherent DNS rebinding risk when relying on application-layer IP validation, as the IP might change between the `getaddrinfo` check and the actual HTTP request. More robust mitigation might involve network-level controls or specific client configurations if available.
