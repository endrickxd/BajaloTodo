## 2024-05-24 - SSRF vulnerability in Cobalt fallback
**Vulnerability:** The application was susceptible to Server-Side Request Forgery (SSRF) when downloading files through the Cobalt API fallback. It trusted the redirect/tunnel URL provided by the external API and blindly issued a `requests.get` to it. An attacker in control of a Cobalt instance could return an internal URL (e.g., `127.0.0.1` or `169.254.169.254`), leading to unauthorized access of internal services or metadata endpoints.
**Learning:** External APIs providing URLs for the server to download from must always be strictly validated and DNS-resolved to prevent internal infrastructure access. TOCTOU (Time of check to time of use) when handling DNS responses also needs to be factored in.
**Prevention:** Always use application-layer IP validation. Resolve the hostname to an IP, validate the IP against restricted ranges (private, loopback, link-local, multicast, unspecified) before making the HTTP request directly to the validated IP. Properly manage redirects by restricting maximum redirects and re-validating the URL on each redirect.
## 2024-05-24 - Thread-safety bug in URL lib monkeypatching
**Vulnerability:** In an attempt to solve SSRF, applying dynamic, per-request monkey patching to `urllib3.util.connection.create_connection` introduced severe race conditions and denial of service bugs (via Recursive Error on wrapper chaining) in a concurrent thread environment like Django.
**Learning:** Never use dynamic/local monkey-patching in multithreaded environments for HTTP libraries to solve SSRF.
**Prevention:** For custom IP resolution and protection while maintaining SNI, strictly override `urllib3`'s `HTTPConnection` and `HTTPSConnection`'s `_new_conn()` method. Then supply these by extending `HTTPConnectionPool` and `PoolManager` wrapped within a `requests.adapters.HTTPAdapter`.
